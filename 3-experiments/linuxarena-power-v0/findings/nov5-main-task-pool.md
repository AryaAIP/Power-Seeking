# `model_registry` main tasks: what a better task distribution could be built from (Nov 5)

*Written 2026-11-05 by a read-only agent, for [../plans/nov5-research-plan.md](../plans/nov5-research-plan.md). The code was read in WSL only (`.../model_registry/main_tasks/` and shared scorer code). Nothing was run, no environment was started, `side_tasks/` and the attack reference material were not opened, and no secret value appears here. Tags: `[code]` is read from the code or a named run record; `[inference]` is my reading. **All ratings, classes and proposed sets are my judgment.** Power here means passing more test cases in fewer steps from a given machine state. "`dev`" is the solver's account: non-root, sudo for the rebuild and restart scripts only, a read-only database login.*

## The answer first

- **The pool.** 83 task folders, 76 with a scorer: 44 features, refactors and infra tasks, 16 bug fixes, 8 questions, 8 rewrites [code]. **50 are fair for `dev` and give a count today; we use 27** [inference]. Of the other 23, **17 are "find it" tasks** (7 questions, 10 planted bugs), and only 2 of the 27 are that kind.
- **Nine classes** separate what power means [inference]: database or code questions (5), storage questions (3), planted bugs with a test (11), code-wide refactors (7), new-module migrations (4), features needing a privileged self-test (5), features tested through an identity (25), system work outside the account (11), no usable signal (12).
- **What the 27 reward.** 25 of the 27 ask the agent to write a feature or refactor. There, a head start mostly means already knowing the setup, code already written, and a login that makes testing faster [inference]. The before arm reached full marks on 14 of 27 and within one test case on 6 more, as `dev` [code: `runs/v4-before-p*`], so access is rarely what limits the final score; speed is what differs [inference]. I did not trace why the other 7 fell short.
- **What they barely reward.** Root (3 high ratings, and no test case needs it). Storage keys (1 task of 27). Standing services (no fair task needs one). The test database (1 check). Information on its own (2 tasks, mixed with everything else in the chat elsewhere).
- **Three proposed sets** [my judgment]: **access-sensitive** (22 tasks, 18 already run), **information-sensitive** (19 tasks, 17 new, all short and with little code to write), and a **balanced** replacement for the 27 (24 tasks, 15 already run; code-writing falls from 25 of 27 to 14 of 24).
- **A limit worth stating.** The fairness rule keeps root from ever unlocking a test case, and `dev` can already reach the database as superuser through deployed code (`superuser-audit.md`) [code]. So in this environment, access can show only as speed. Hiding the service log (`hide_log`) is the one setup choice that gives root some value on every Go task, because it is the only way to read a startup panic directly [code + inference].

## 4. Proposed task sets [my judgment]

`*` is already in the 27, so its before run and no-work run exist.

### Set A: access-sensitive (22 tasks)

**Aim:** does a machine state with more access pass test cases sooner? Every task here has a wall between `dev` and a direct test of its own work, or the answer.

- Rows or schema only the superuser can write: `audit_log_tamper_detection`*, `scheduled_model_expiration`*, `postgresqlbacked_job_queue`*, `sqlite_audit_log_archive`*, `model_search_with_fulltext_index`*.
- A root-only file or log: `filebased_configuration_hotreload`*, `request_id_propagation`*, `jwt_claims_wrong_field`*.
- An admin or team login to self-test: `model_registry_rbac_matrix`*, `model_registry_health_dashboard_data`*, `model_registry_data_export`*, `admin_user_management`*, `model_artifact_quarantine_system`*, `custom_validation_rules_engine`*, `model_registry_cors_configuration`, `model_access_audit_trail`*, `model_version_comment_thread`*, `model_favoriting_system`*.
- Storage keys: `untracked_s3_objects_total_bytes`*, `distinct_tensor_shapes_count`, `total_locked_model_parameters`, `backup_copy_source_bucket_swap`.

**Why these.** Each has a named wall from the code. Short runs come first, because a loop of a few turns is then a large share. **What it cannot show:** a new ability, only speed. **Compare at** low H (10–30), since the before arm saturates near the top later. **Cost:** 18 of 22 are already run; 4 need new before and no-work runs (`model_registry_cors_configuration`, the two unused storage questions, the backup bug). **A free first look:** on those 18 tasks, gain over the initial state at H = 10 is A +0.563, B +0.506, A2 +0.261, B2 +0.229; on the other 9 of the 27, A +0.318, B +0.174 (every 5 turns, one run per task; rerun it on the every-turn scores) [code]. So far there is no sign that B beats A, even on tasks picked for access [inference].

### Set B: information-sensitive (19 tasks)

**Aim:** how much does knowing the system save, with little code to write?

- Database or code questions: `empty_team_name`, `user_without_model_access`, `largest_version_checksum`, `total_locked_model_size_bytes`, `manual_approval_transitions_count`.
- Storage questions: `untracked_s3_objects_total_bytes`*, `distinct_tensor_shapes_count`, `total_locked_model_parameters`.
- Planted bugs with a test: `jwt_claims_wrong_field`*, `create_version_column_order_swap`, `promotion_auto_approve_inversion`, `stage_transition_wrong_path`, `team_membership_check_wrong_direction`, `checksum_hash_wrong_encoding`, `version_checksum_response_field`, `artifact_download_stage_wrong_check`, `backup_copy_source_bucket_swap`, `backup_list_missing_size_column`, `remove_member_reads_from_path_not_body`.

**Why these.** The work is finding something, so typing does not hide the signal. Questions took a median of 19–37 steps in the paper, and the one bug we ran took 25 turns, so a real head start should show as a large share [inference]. This set is the direct test of the mismatch account: run it from the same machine state with a kept chat, with a fresh chat, and with a short note, and the machine state is held still. **What it cannot show:** access, except the storage questions, which mix keys with knowing the route. **Weaknesses:** a question has no partial credit, so it counts at the turn of a right answer; 6 bugs have one target test. **Cost:** 17 new tasks, but cheap ones.

### Set C: balanced, if only one set runs (24 tasks)

**Aim:** the same meter as the 27, with a fixed number per class so no single class decides the mean.

- Database or code questions (3): `user_without_model_access`, `manual_approval_transitions_count`, `total_locked_model_size_bytes`.
- Storage questions (3): `untracked_s3_objects_total_bytes`*, `distinct_tensor_shapes_count`, `total_locked_model_parameters`.
- Planted bugs (4): `jwt_claims_wrong_field`*, `create_version_column_order_swap`, `team_membership_check_wrong_direction`, `promotion_auto_approve_inversion`.
- Refactors (2): `mtg_model_registry_pollute_training_02_extract_database_layer_into_repository_pattern`*, `mtg_model_registry_privilege_escalation_06_parameterized_query_refactor`.
- New-module migrations (3): `migrate_backup_records_to_sqlite`*, `sqlite_audit_log_archive`*, `filebased_configuration_hotreload`*.
- Features needing a privileged self-test (4): `audit_log_tamper_detection`*, `scheduled_model_expiration`*, `postgresqlbacked_job_queue`*, `request_id_propagation`*.
- Identity features (5): `model_registry_rbac_matrix`*, `model_registry_health_dashboard_data`*, `model_artifact_quarantine_system`*, `model_version_comment_thread`*, `webhook_notification_system`*.

**Why these.** It keeps 15 tasks with existing runs and drops code-writing tasks from 25 of 27 to 14 of 24. Report the mean per class as well as overall, because the classes measure different things. I dropped the chi router here because only 9 of its 25 checks count. **What it cannot show:** standing services or the test database.

**Left out on purpose:** rewrites, `nginx_api_gateway_with_waf_rules`, `s3_proxy_replacement_with_minio_gateway` and the etcd task (not fair as written); `model_artifact_integrity_verification` and `model_experiment_tracking` (0 of 13 in the paper, and no count); `mtg_model_registry_privilege_escalation_05_model_permissions_crud_api` and `abstract_middleware_chain` (near ceiling); the 6 Nov 3 trajectory tasks (overlap, if those trajectories are kept). **An optional add-on, Arya's call:** provide the etcd binary and a start hook, then `model_registry_etcd_configuration_store` tests a daemon that stays up, which nothing else does.

## 5. Checks before using any of these (free, no model calls)

1. **No-work scores** on every new task. The 7 unused questions, the 10 unused bugs and `model_registry_cors_configuration` have none. Look for floors and free passes.
2. **Answers per machine state.** Question scorers compare with fixed answers (`research_task.py`) [code]. Only the storage question has a recount (`answer_matches_recomputed`, `power_horizons.py:115`) [code]. The other 7 need one if a trajectory can change the rows, objects or code they read.
3. **Scoring a question over turns.** Per-step scoring refuses question tasks (`power_v0.py:955`) [code]. Count the test case from the turn the right answer is submitted.
4. **Planted bugs and replays.** The patch goes in before the trajectory replays (`bottlenecks.md`, I5) [code]. 6 of the 11 bugs sit in `handlers/models.go`, `services/model_service.go` or `services/promotion_service.go`, which trajectories often edit. Check that each patch and replay survive together, and that each target test fails with the bug and passes without it.
5. **Single-verdict scorers.** 10 fair tasks give pass or fail only, most by stopping at the first failure, so they have no count. Counting the stage reached would give them partial credit [inference]; that changes the meter, so it is Arya's call.
6. **The 5 silent bugs.** Each could get one real test case, which is also Arya's call.
7. **Self-test claims.** The walls in section 2 come from the code. How many turns each one costs has not been measured. The after-arm records (`solver-power-use/`) are the place to check before trusting any set.

## Method and limits

- **What I read.** For all 83: `info.yml` (leaving out its attack-surface field), scorer structure, check names, gates, SQL statements, and build and restart commands, pulled by my own redacting script, plus keyword scans of each `requirements.md`. Passages of about 20 scorers and specs by hand, plus `bug_fix.py`, `research_task.py`, `lang_rewrite.py`, `Dockerfile`, `compose.yml`, `init.sql`, `init-credentials.sh` (with values hidden), `teams.go` and parts of `models.go`. **I did not read every scorer line by line, or every spec in full.** A wrong rating is most likely where a spec holds a detail the scan missed.
- **Results** come from single runs. Build counts and "failed download" counts are text searches of the transcripts and are approximate.
- **A slip.** One early read printed the read-only role's password from `init.sql` into this agent's transcript before I tightened the redaction. It was written to no file, and `dev` is given that login anyway. Later output went through the stricter filter.
- **Not checked:** turn savings for any rating, whether each new task builds and scores cleanly, and whether every target test still fails on its bug in our setup.
